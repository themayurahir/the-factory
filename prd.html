Product requirements · plan

Software Factory: PRD & Plan

As of 2026-10-03 · Draft for review

Give it one vague idea. Get back a working, tested, reviewed repo and a report of what was built and why.

01Vision and problem

Today a person drives every step: research, spec, plan, code, review, test. Agents can now do each step well. Nothing chains them together with shared memory, quality gates and a budget.

The factory is that chain: an orchestrator plus a set of agent roles. The coding itself is handed to Claude.

Input
One or two sentences, in any form.
Output
A git repo with code, tests and a README; the PRD and plan; a run report covering decisions, cost and gaps.
Your role
Answer up to 5 clarifying questions. Approve the spec. Approve the release.

02Goals, non-goals and metrics

Goals

  • Idea to running repo end to end, unattended between gates.
  • Resumable runs: a crash or a stop picks up at the last finished stage.
  • Every stage leaves an artifact on disk.

Non-goals for the MVP

  • Multi-tenant SaaS.
  • Any UI beyond the CLI and the HTML report.
  • Deploying to production.
  • Mobile apps.
  • Editing large existing codebases.

Metrics

03Core flow

  1. Intake. The idea gets at most 5 clarifying questions. Gate: you answer
  2. Deep research. Prior art, libraries and risks, with sources.
  3. Spec / PRD. What gets built, for whom, and the acceptance criteria. Gate: you approve
  4. Plan. Architecture plus a task graph with acceptance tests per task.
  5. Build. Parallel builder agents in isolated git worktrees, test-first.
  6. Review. Code and security reviewers. Failures loop back to Build, max 3 loops.
  7. Verify. An independent evaluator runs the app and the tests itself.
  8. Deliver. Repo, report and release. Gate: you approve

05Architecture

Delivery form

The factory starts as a Claude Code plugin and graduates to a standalone Python orchestrator. The plugin's agents and skills are reused, not rewritten.

FormWhat it isRole in the factory
SkillInstructions loaded into one sessionA building block: one skill per role (e.g. write PRD). Too small to be the factory: it can't enforce gates, resume or a budget.
PluginA bundle of agents, skills, a /factory "<idea>" command and hooks, installed into Claude CodePhases 0–1. Packages the existing planner, architect, tdd-guide, reviewers and deep-research. Each stage runs as a subagent and writes /factory/*.md. Hooks enforce guardrails: budget, no production credentials, no destructive commands.
Standalone programA Python state machine on the Claude Agent SDKPhase 2+. Unattended multi-hour runs, deterministic resume from run.json, cost ledger, parallel sandboxes, CI triggers. It loads the same plugin, so only the conductor changes.

Trade-off: in the plugin, Claude itself decides the stage order. That is fine for the MVP but not reliable enough for unattended runs, so the conductor moves to code in Phase 2.

06Build vs reuse

Build on Claude Code. Ship the MVP as a Claude Code plugin, then move the conductor to the Claude Agent SDK in Phase 2. Borrow the spec/plan ideas from Spec Kit and BMAD. Skip the stale frameworks.

07MVP and roadmap

Phase 0 tasks

  • Plugin scaffold: plugin.json, agents/, skills/, commands/factory.md.
  • Wire the existing agents and skills to the stages: deep-research, prp-prd, planner / prp-plan, prp-implement / tdd-guide.
  • Stage artifact contract: each stage reads and writes its files under /factory/.
  • Intake: at most 5 questions, answers saved to idea.md.
  • Run pytest; write report.html.
  • Run one sample idea end to end.
  • Run 5 sample ideas; record pass or fail for Gate 1.

08Risks and guardrails

RiskMitigation
A vague idea leads to the wrong productClarifying questions at intake, then the spec gate.
Runaway cost or loopsBudget cap, max iterations per stage, stall detection.
Agents grade their own workA separate evaluator runs the tests itself.
Destructive or unsafe actionsSandbox, no production credentials, worktrees, release gate.
Quality falls off on big appsMVP scope capped at small apps; task graph with acceptance tests.
Context lost across stagesEvery stage writes an artifact to disk; the next stage reads files, not chat.
